KiCad‑iOS · How It Works

Real source. Real program. New platform.

Nothing here is a recreation. The port compiles upstream KiCad 10.0.1's own source code for iPadOS — KiCad's own windows, menus and buttons — and answers the four walls between that source and a tablet with working machinery.

/ The four walls

1

The wxQt bridge

KiCad's interface is written in wxWidgets, which has no iOS port. Here it runs on wxWidgets' Qt backend — wx 3.3 over Qt 6.9.3 — and Qt runs natively on iOS. KiCad's own build system already recognises the Qt port of wx, so KiCad itself builds against it unchanged in structure.

2

Single-process Kiway

On the desktop, KiCad's editors run as separate processes. iOS apps are single-process, so each editor ships as a kiface module loaded inside the one app process, opening as its own window — the manager's launcher starts each tool in-process.

3

Embedded Python

KiCad's build requires Python, and its scripting is part of the program. A full CPython 3.13 sysroot is cross-compiled for iOS and embedded in the app, so Python initialises at startup and import pcbnew resolves to the real compiled module.

4

A canvas that fits the platform

The desktop canvas is OpenGL; iOS offers no OpenGL. KiCad's built-in Cairo software canvas carries the editors on iPad — correct rendering on the platform's own terms. V1 closes the last detour: the canvas factory itself returns Cairo, so no path attempts OpenGL first. The 3D viewer is the one tool that stays OpenGL-bound, and it does not work on iOS — stated plainly.

/ Libraries and files, in the box

A KiCad install is only as good as its libraries. The bundle carries KiCad 10.0.1's libraries complete: 222 symbol libraries and 155 footprint libraries, the default library tables resolving straight to them, 19 project templates and the demo projects — plus, in V1, the JSON schemas the manager validates its plugin data against. File sharing is on: projects live in the app's Documents folder and move on and off the iPad the normal way. The app's own document lists work over that shared folder — no system file picker is involved.

/ One of everything

Verified before it ships

The bundle carries exactly one libpng, one zlib and one expat, shared by every component — and the build fails closed if a bundled duplicate tries to sneak back in. (An early build shipped two libpng copies with mismatched memory layouts and crashed at startup on device; the gate exists because of it.) Every package passes automated gates before release: a full symbol-closure audit across all images, Qt resource checks, the libpng unity gate, a content gate proving the bundled libraries and editor modules ship complete, and deep signing verification.

On top of those, a binary-inspection gate reads the shipped executable itself and proves the port's code is actually compiled in — disassembling the canvas-selection code, checking for the titlebar, gesture, clamp, keyboard and status-bar machinery of the current release, and confirming the previous release fails every one of those counts. File presence is never accepted as proof. A build that fails a gate does not ship.
